# 設計判断の記録

「なぜそうなっているか」と、検討して見送った案。仕様の本文は[language/](language/)にある。
新しい判断をしたら、末尾に追記する。書式は **決定 / 理由 / 見送った案**。

## 言語

### D1. `template <T>`は直後の宣言1つにだけ効く
- **決定**: C++と同じ。`type`・`export type`・`declare function`・`function`(`local`/`const`も)・`class`・クラスのメソッド(演算子を含む)に付けられる。2つ目の宣言で`T`を使うなら、そちらにも`template <T>`が要る。
- **理由**: 利用者がC++の挙動を想定していた(「C++ではこれは合法だった気がする」)。適用範囲が局所的で、`T`がどこまで見えるかを読み手が追わなくて済む。
- **見送った案**: 以降のファイル全体に効く宣言(複数の演算子で型引数を共有できるが、範囲が曖昧になる)。共有したいときはユニオン型(`type Arithmetic = Vector3 | number`)を使う。

### D2. ジェネリクスの不一致は、宣言ではなく呼び出し側で報告する
- **決定**: `declare function add2(a: T, b: string): number`のような宣言自体は通し、`add2(1, 2)`のように呼び出しで型が合わないときにエラーにする。型引数は引数から推論し直し、食い違いは「type parameter 'T' was inferred as number but argument 2 is string」と出す。
- **理由**: 宣言側に「推論できない型」があっても、使われなければ害がない。呼び出しごとに診断したほうが、利用者が直す場所に赤線が出る。
- **範囲**: 呼び出しの型検査は`declare function`と`template`つき関数だけ。通常の関数の引数は従来どおり検査しない(既存コードを壊さないため)。

### D3. ユニオン型の代入と`::`
- **決定**: ユニオンを代入するには全メンバーが受け側に入る必要がある。`::`はどれか1つのメンバーと関連していれば許す。ユニオンの値への演算子は、どのメンバーか追跡しないので検査しない。`T | nil`は`T?`と同じ。
- **理由**: 演算子オーバーロードの引数(`Vector3 | number`)を表すことが動機。追跡まで入れると型の絞り込み(narrowing)が要り、スコープが大きくなる。

### D4. `declare global class`はエラー
- **決定**: `declare class`はもともと修飾なしで使えるので、`declare global class`は「a declared class is already global」というエラーにする。
- **理由**: 黙って受け入れると、`global`の意味が`declare`の他の形と食い違う。エラーの文言で正しい書き方を示す。

### D5. キャスト`::`の優先順位と出力
- **決定**: 二項演算子より強く、単項演算子より弱い。`::name::`はラベルなので、`::`の後に`識別子 ::`が続く並びはキャストにしない。キャストの連鎖は括弧で書く。型の側の`<`はジェネリクスとして読まれる。
- **理由**: Luauの`::`と同じ位置づけに揃え、ラベル構文(Lua 5.2由来)と共存させるため。
- **出力**: Luauは`(expr :: T)`と**括弧で束ねて**出力する(直後の`<`を型引数と読ませないため)。Lua 5.4は消去して`-- cast: ...`のコメントを残す。

### D6. 標準ライブラリは`.luard`と同じ文法のテキストで持つ
- **決定**: `stdlib.rs`がLua 5.4/Luauの標準ライブラリを型つき宣言として持ち、`modules::parse_definition`で読む。色分けも同じ定義から引く。多値の戻り値とオーバーロードは`any`と可変長で逃がす(最初の値の型だけ持つ)。
- **理由**: 定義の書式を1つに統一でき、利用者の`.luard`と同じ仕組みで上書きできる(自分で宣言した名前は標準を隠す)。
- **見送った案**: Rustの構造体で手書きする(型の追加のたびにコードが要る)。

### D7. インスタンスメソッドの呼び出しは、型を知るチェッカーが`:`に直す
- **決定**: ソースでは`obj.method(args)`と書く。どのメソッドが`self`を取るかは受け手の型で決まるので、チェッカーが呼び出しの位置を記録し、`method_calls`が`obj:method(args)`へ書き換える。
- **理由**: 「コロンとドットを使い分けない」が言語の方針。引数ずれのような分かりにくいエラーを避ける。構文だけでは型が分からない(`v.set(...)`が`v:set(...)`になる必要がある)ので、型検査の結果に依存させた。
- **注意**: 受け手の型が確定しないと`.`のままになる。型の分からない値のメソッド呼び出しは書き換えない。

### D8. `import type`は型専用で、実体の束縛とは別
- **決定**: `import type mod`は`.luard`の宣言だけを読み、実行時コードを出さない。実体は対象ランタイムに合わせて利用者が同名の`local`/`const`で束縛する(意図的なシャドーイング)。
- **理由**: 実体の提供方法(`require`、C/C++バインド、グローバルテーブル)はLuarではなく実行環境が決める。旧`import module`は廃止した。
- **曖昧な未修飾名**: 複数のモジュールが同名を宣言していても、その未修飾名が使われなければエラーにしない。使われた場合だけ曖昧参照のエラー。

### D9. `import type name from "相対パス.luard"`
- **決定**: 同じディレクトリの`name.luard`だけでなく、`from`で相対パスを指せる。拡張子は`.luard`のみ、絶対パス不可(`!include`と同じ規則)。パスの解決はコンパイラが行い、エディタは`luar imports`で問い合わせる。
- **理由**: エディタ側(TypeScript)にパス規則を二重に持たせない。`!include`と`import type`のパス規則を揃えて覚えやすくする。
- **見送った案**: 絶対パス・拡張子の自由化(プロジェクトの移動で壊れる)。

### D10. `!include`は末尾の`return <名前>`が必須で、クラスも返せる
- **決定**: 取り込まれるファイルは最後に`return <識別子>`で、モジュールとして渡すものを決める。テーブルだけでなく`class`の名前も返せる。`static`メソッドだけのクラスは名前空間として使える。`return`が無いときは、最後に宣言されたクラス(なければ`local`/`const`/`function`)の名前を使ったヒントをエラーに付ける。
- **理由**: 返す対象が明示されていれば、衝突時の改名や、メンバー定義の自動生成(`.luard`なしの`import type`)で扱いやすい。
- **関連する判断**: `static`メソッドだけのクラスでも、未使用の`new()`と`__index`は出力されたまま(コード生成は変えない)。出力の最適化より仕様の単純さを優先した。

### D11. 名前の衝突は、include側だけを改名する
- **決定**: 展開したソースのトップレベルの名前が、include元の束縛と同じなら、include側を`<元の名前>__<束縛名>`へ改名する。メンバー名・テーブルのキー・ラベル・文字列・クラスのメンバー宣言名は改名しない。改名が必要な名前がテンプレート文字列の`{}`内にあるときは、安全に改名できないのでエラー。
- **理由**: 文字列置換だとメンバー名まで壊れる。トークン単位で変数・クラス名・型名の参照だけを対象にした。

### D12. 型注釈の出力: Luauは残し、Lua 5.4は消す
- **決定**: Luauターゲットは型注釈をLuauの構文でそのまま出力する(関数の引数・戻り値・型引数、local/const、`type`、キャスト、クラスのメソッド)。Lua 5.4ターゲットは消去し、元の宣言を`--`コメントに残す。
- **理由**: 以前は常に消去していたため、出力のLuauをAnalyzeにかけると`T`や`num`が無注釈になり、`No valid instantiation could be inferred`のような誤報が出た。型エラーはバイトコードの最適化を弱めない(Luauのコンパイラは型チェッカーの結果を見ない)が、ネイティブコード生成(`--!native`)では引数の注釈が特殊化に使われる。
- **出力コードに宣言が無い型名は`any`**: クラス名、`import type`した型、`declare class`の型。`Dog?`は`any?`、`{ Dog }`は`{ any }`。クラスをLuauの型として出力する(`typeof(setmetatable(...))`)ことは見送った。
- **既知の取りこぼし**: `local f: (number) -> number = function(x) ... end`は`local function f`に変換されるため、`f`の型注釈は出力されない(引数と戻り値の注釈は残る)。再帰を壊さないため、この変換自体は維持した。

### D13. `using`: 明示マーカー、エラー時も解放、`free`は1回だけ、親へ連鎖
- **決定**: `using 名前 = 式`で宣言した変数だけを、スコープ脱出で`free()`する(`local`は何もしない)。`return`/`break`/`continue`/`error()`のどれで抜けても呼ぶ。`free`は何度呼んでも1回だけ実行し、子の`free`の後に親の`free`を自動で呼ぶ。
- **理由**:
  - Luau/Luaは参照渡しで、所有権の概念が無い。すべての`local`を自動解放にすると、`return`した値、テーブルに保存した値、クロージャが握った値まで解放して、使用中に壊れる。エスケープ解析で補うより、利用者が明示するほうが安全で実装も単純。
  - 「イベントを必ず切断する」用途には、エラーで抜けるときも呼ぶ必要がある。
  - 明示的な`free()`とスコープ脱出が重なるので、冪等にする。
  - 親のリソースの解放漏れを防ぐ(C++のデストラクタの順序)。`super.free()`を書いても、解放済みのため害はない。
- **実装**: Lua 5.4は`local x <close>`と`__close`。Luauは`pcall`で包むクロージャ(コストはスコープごとにクロージャ1つ)。詳細は[architecture.md](architecture.md)。
- **制約**: `using`のある関数で`goto`/ラベルは使えない。`repeat ... until`の本体直下とif式の中には書けない。値は`free`を持つクラス(`Class?`も可)でなければならず、型が決まらない値はエラー。
- **見送った案**: 型が決まらない値への実行時チェック(`if x.free then ...`)。静的に確かめられるものだけを許す方針。

### D14. 継承したメソッドを隠すには`override`が要る
- **決定**: 親に同名のメソッドがあるとき、`override`なしの再定義は禁止。`override`は親に同名のメソッドが無ければエラー。シグネチャ(名前・引数・戻り値)は完全一致。`free`も例外ではない(`function free() override`と書く)。
- **理由**: 意図しない上書きを防ぐ。フィールドは自由に上書きできる(`override`は適用されない)。

## 実装方針

### I1. 正式な実装はRustの`luar-rs`
- **決定**: `luar/`のTypeScript frontendはCLI・codegenとしては非推奨にし、`luar-vscode`の寛容な編集中インデックスと互換テストのためだけに残す。
- **理由**: 型検査・補完・色分けを2つの実装で保つコストが大きかった。エディタの意味的な判断はコンパイラに問い合わせる(`luar check|complete|tokens|definition|imports`)。

### I2. 色分けと定義ジャンプは、構文解析に依存しない
- **決定**: `symbols.rs`は字句ベースのスコープ解析で、ASTを使わない。メンバー参照(`x.name`)の解決だけは型が要るのでチェッカーに問い合わせる。
- **理由**: 入力途中は構文エラーになりやすい。字句解析ができれば色分けと定義ジャンプが動くようにする。

### I3. エラー回復と「不明なグローバル」の連鎖を止める
- **決定**: 壊れた`.luard`は`*_lossy`が飛ばして読み進める。読み込みに失敗した定義がある間は、未定義グローバルの警告を出さない(`imports_incomplete`)。
- **理由**: 宣言が読めないだけなのに、その宣言で定義されるはずの名前が全部「不明なグローバル」になる連鎖を避ける。構文エラーが1つあるだけで画面が赤くならないようにする。

### I4. 診断の位置は元ファイルに戻す
- **決定**: `!include`で行がずれるので、診断・色分け・定義ジャンプは`ExpandedSource.origins`で元のファイルと行に戻す。
- **理由**: インクルードされたファイルのエラーを、インクルード先の正しい行に出すため。

### I5. 補完は「問い合わせ用の呼び出しに書き換えて通常の解析に通す」
- **決定**: カーソル位置の式を`__luar_probe(<recv>)`/`__luar_scope()`に書き換え、チェッカーがその呼び出しに到達した時点の型環境を記録する。
- **理由**: 型の判断を診断と同じチェッカーに任せ、補完専用の型推論を別に持たない。入力途中で閉じ括弧が足りなくても、補った版で解析する。

## エディタ拡張

### E1. semantic tokensが効かなかった原因は、設定の重複
- **事実**: `package.json`に`configurationDefaults`が2つあり、後のものが前のものを上書きして、`[luar]`のsemantic highlightingが無効になっていた。`editor.foldingStrategy`の`folding.markers`の誤用が、ミニマップの文字が巨大になる原因だった。
- **教訓**: 拡張の設定は1か所にまとめる。「何も色が付かない」ときは、まず`package.json`の重複を疑う。

### E2. 拡張を変えたらVSIXの再生成と再インストールが必要
- **事実**: 拡張はVSIXから使われるので、ソースを直しても`npm run build`だけでは反映されない。`.\tools\Update-LuarExtension.ps1`(コンパイラも更新するなら`-WithCompiler`)を実行し、VS Codeを再読み込みする。
